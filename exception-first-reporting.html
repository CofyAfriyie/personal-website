Reporting practice

Why showing errors matters: an error does not mean everything failed

An error does not mean everything failed. It means something needs investigating, and a good report shows it instead of hiding it.

Afriyie Kofi Owusu-Ansah8 min readAnalytics & controls

Most reports are designed around totals: revenue, cost, conversion, performance, variance. That is useful, but it is only half the job. A total can look precise while its underlying records contain duplicates, stale classifications, missing references, or unexplained differences.

Exception-first reporting adds a second question beside every headline: what could make this number wrong? It then makes the answer visible enough for a reviewer to act on it.

Trust grows when a report shows its limits as clearly as it shows its results.

The problem with a clean dashboard

Imagine a monthly spending report showing GH₵12,000. The number may be correct, but a decision-maker cannot tell whether it includes every transaction, whether a refund was counted twice, or whether part of the total came from a figure typed into a summary cell months ago.

A visually polished dashboard can make this worse. Formatting creates confidence before the data has earned it. The solution is not a messier dashboard. It is a controlled path from source records to calculated results, with exceptions shown separately.

A practical four-part structure

01 · Source

Keep the original record, its native reference, and the date it entered the system.

02 · Transformation

Document the rules that clean, classify, join, or exclude each record.

03 · Result

Calculate summaries from the controlled detail instead of typing finished figures.

04 · Exception

Route anything uncertain, unmatched, duplicated, or stale into a visible review queue.

What belongs in an exception queue?

An exception is not automatically an error. It is a record that needs a decision or stronger evidence. Useful exception types include:

  • Unmatched: a record exists in one source but has no corresponding record in another.
  • Probable match: the amount and timing align, but the reference is incomplete.
  • Duplicate candidate: two records look identical but may represent separate real events.
  • Stale input: a manual value has not been refreshed for the current reporting period.
  • Rule conflict: two classification rules could reasonably apply to the same record.

A small synthetic example

The main report can count only confirmed records, or show confirmed and probable results side by side. The important part is that the policy is explicit and reproducible.

Replace snapshots with formulas

If a figure can be derived from controlled detail, it should be calculated. Hard-coded totals drift when new records are added or old records are corrected. Formulas, measures, or queries keep the summary tied to the evidence.

Some values must remain manual: exchange rates selected for a valuation date, balances reported by an external platform, or assumptions chosen by management. Label those cells as inputs, record their source and date, and keep them separate from calculated outputs.

Design the review process, not only the report

Every exception should have an owner, status, reason, and next action. A simple workflow is enough:

  1. Capture the exception without guessing.
  2. Assign the person or source that can resolve it.
  3. Record the evidence used for the decision.
  4. Update the underlying record, then let the report recalculate.
  5. Keep a short change log so the correction can be explained later.

The standard I use

A dependable report should let another person answer five questions: Where did this number come from? Which rule transformed it? What did we exclude? What remains uncertain? What changed since the last version?

When those answers are easy to find, reporting becomes more than presentation. It becomes a decision system people can inspect, challenge, and improve.
